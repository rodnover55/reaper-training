# Design

## Context

Мотивация — `proposal.md`, раздел Why.

**Где сейчас решения тренажёра.** `Trainer` (`src/trainer.cpp`) держит
состояние и решает:
- что делать на перемене транспорта (`onPlayState`, `start`);
- какую атаку звука взять в строки (граница запуска, остановка);
- какую ноту MIDI взять (`pollMidi`: устройство, вход только для управления,
  `pp` < 0, начало ноты, count-in, мёртвое время);
- что писать в строку состояния (`currentStatus`);
- как идёт калибровка (`startCalibration`, `pollCalibration`,
  `feedCalibration`, `finishCalibration`, обрыв без звука, прерывание
  запуском).

Многие из этих функций сами REAPER не зовут, но живут в классе, который без
REAPER не создать:
- конструктор читает настройки из ExtState и скорость проекта;
- `AudioInput` в конструкторе регистрирует аудиохук;
- поиск входов зовёт `GetInputChannelName` и `GetMIDIInputName`.

Остальные читают REAPER прямо по ходу решения: позицию (`movedAgo`,
`followPlayback`), петлю (`loopWrapped`), историю MIDI-входа.

Окно (`src/window.cpp`) решает:
- что писать в строку состояния (`statusText`);
- какая панель калибровки видна (`panelOf`);
- какие кнопки калибровки видны и доступны (`placeCalibrationButtons`);
- как правка контрола меняет настройки (`editedSettings`).

Без REAPER проверяется то, что уже вынесено в библиотеки `libs/grid`,
`libs/onset` и `libs/concurrency`: сетка, свод нот в строки, модель показа,
поиск атак, математика калибровки. Изоляцию каждой библиотеки от хоста и ОС
проверяет тест `<библиотека>_isolation` (`cmake/CheckIsolation.cmake`).

**Зацепки для проверок вживую.** Только в конфигурации Debug (макрос
`TRAINING_DEBUG_BUILD`) модуль регистрирует 15 функций ReaScript
`TrainingDebug_*` (`API_` и `APIvararg_`, `src/debug_actions.cpp`):
- нажатия в окне — `ClickButton`, `ClickCheckbox`, `TypeText`, `DragGauge`;
- настройки и вход — `SetSettings`, `SetInput`, `SetHitWindow`,
  `SetEnergyRatio`;
- ноты и звук без гитары — `AddNote`, `CalibrateFromItem`;
- рисование окна в файл — `SnapshotRows`, `SnapshotGauge`;
- переменные настроек REAPER — `ConfigVar`;
- отметки скрипта в журнале — `Journal`.

Ещё там два отладочных действия: сверка атак последнего запуска с айтемом и
печать тактов. Для них в `Trainer`, `AudioInput` и окне есть код только для
проверок: `addTestNote`, `startCalibration(samples, …)` с `TestSound`,
`lastRun`, `lastMidiRun`, `setEnergyRatio`, `clickButton`, `clickCheckbox`,
`dragGauge`, `typeText`, `snapshotRows`, `snapshotGauge`. На эти функции
опираются задачи и разведки архива: `add-input-calibration`,
`add-timing-offset`, `bar-per-row-display`, `add-midi-input`.

**Что есть для проверки чёрным ящиком.**
- Xvfb стоит; на нём есть расширение XTEST — поддельный ввод мышью и
  клавиатурой работает, в отличие от рабочего стола пользователя под Wayland.
- REAPER запускается на `:99`, скрипты Lua доходят до него через
  `reaper -nonewinst`.
- Ноты MIDI подаёт виртуальная MIDI-клавиатура (`StuffMIDIMessage`).
- Переменные настроек меняет `set_config_var_string`.
- Журнал тренажёра пишется во всех сборках.

## Goals / Non-Goals

**Goals:**
- Модуль расширения — связка без собственных решений: читает REAPER, передаёт
  данные чистому коду и исполняет ответ.
- В модуле нет кода только для проверок ни в одной сборке.
- Проверка вживую — чёрный ящик и подтверждает только связку.

**Non-Goals:**
- Поведение тренажёра для пользователя не меняется.
- Поведение REAPER тестами не покрывается: его выясняет разведка
  (`findings.md` изменения).
- Звуковой путь целиком (звук → атака → строка) вживую не проверяется: без
  источника звука на входе этого не сделать. Его покрывают юнит-тесты поиска
  атак и времени ноты; вживую — только то, что хук получает звук выбранного
  канала.

## Decisions

### D1. Чистый код тренажёра — библиотека `libs/trainer`

Решения тренажёра уходят в новую библиотеку `training_trainer`
(`libs/trainer`, пространство имён `training::trainer`) с собственной
проверкой изоляции `trainer_isolation`. Всё, что даёт REAPER, она получает
параметрами: начало и конец запуска, позиции, события истории MIDI-входа, куски
звука, сведения о входе, время монотонных часов. Ответ — решение или новое
состояние; REAPER она не зовёт.

Отвергнуто: чистые файлы в `src/`, которые тесты собирают к себе, как
`journal.cpp`. Изоляцию от REAPER тогда не проверить тестом.

### D2. Модуль — связка

`Trainer` и `AudioInput` в `src/` держат ядро из D1 и связывают его с REAPER:
- получают уведомления поверхности управления, кадры таймера и блоки звука
  аудиохука;
- читают у REAPER то, что нужно ядру;
- исполняют решения ядра: журнал, сохранение настроек.

Собственных условий о транспорте, нотах и калибровке у связки нет.

### D3. Окно рисует состояние тренажёра из ядра

Ядро держит состояние тренажёра — данные для отрисовки, а не элементы окна:
- состояние измерения: ждёт ли тренажёр запуска, меряет ли, нет ли входа, не
  выключен ли вход MIDI; имя и вид входа, компенсация задержки, скорость,
  прервал ли запуск калибровку;
- сессию калибровки и её этап: тишина, ноты, нет звука, итог;
- порог, который калибровка посчитала, но не поставила, — для «Apply
  anyway».

Всё видимое окно строит само из этого состояния и настроек: текст строки
состояния, панель калибровки, видимость, доступность и подписи кнопок; оно же
расставляет контролы и рисует. Модель показа строк тактов уже в `libs/grid`
(`present`).

### D4. Проверка вживую — чёрный ящик на Xvfb

Инструменты в `tools/live/` (findings.md, R1–R4):
- запуск REAPER на Xvfb с отдельным каталогом ресурсов
  (`reaper -cfgfile`): модуль из сборки, свои настройки тренажёра и журнал,
  окно тренажёра — в плавающем доке, то есть отдельное окно X, главное окно
  REAPER — рядом с ним, не поверх; каталог ресурсов пользователя не
  трогается;
- выход — `reaper -nonewinst -closeall:nosave:exit`;
- запуск скрипта Lua через `reaper -nonewinst`;
- щелчок мышью в контрол окна тренажёра через XTEST: координаты — из
  `src/views/forms.rc`, диалоговые единицы на масштаб SWELL; пункт
  выпадающего списка — в окне списка по высоте пункта;
- снимок окна тренажёра через Xlib (`XGetImage`).

Скрипты управляют REAPER только публичным API, ноты MIDI подают виртуальной
клавиатурой. Результат читается по журналу тренажёра и снимкам.

Отвергнуто: зацепки внутрь модуля — проверяют логику не тем способом и
держат тестовый код в модуле.

### D5. Код только для проверок удаляется

Удаляются:
- `src/debug_actions.cpp` и `src/debug_actions.hpp` целиком;
- отладочные функции окна;
- `Trainer::addTestNote`, `startCalibration(samples, …)` и `TestSound`,
  `lastRun`, `lastMidiRun`;
- `AudioInput::setEnergyRatio` и `energyRatio`, `onset::Detector::setEnergyRatio`;
- макрос `TRAINING_DEBUG_BUILD`.

Конфигурация Debug остаётся — для отладчика.

Факты о поведении REAPER разведки выясняют скриптами Lua через публичный API
REAPER (скилл `reascript`).

### D6. Правило проверки задач

Правило задач в `openspec/config.yaml`: проверка задачи — юнит-тесты решений
тренажёра и проверка связки с REAPER чёрным ящиком (публичный API REAPER из
скриптов, виртуальная MIDI-клавиатура, щелчки и снимки окна на Xvfb, журнал
тренажёра). Поведение REAPER проверки задач не проверяют. Проверок с
участием пользователя нет.

## Risks / Trade-offs

- [Большая переделка `Trainer`, пока идёт `remove-poll-timer`] → изменение
  делается после архива `remove-poll-timer`, по одному решению за задачу, с
  тестами в той же задаче.
- [Щелчок по координатам ломается при перестановке контролов] → координаты
  контрола берутся из той же раскладки, по которой окно расставляет контролы
  (разведка 1.1), а не задаются числами в скрипте.

## Migration Plan

Для пользователя ничего не меняется. Отладочная сборка больше не
регистрирует `TrainingDebug_*` и отладочные действия.
